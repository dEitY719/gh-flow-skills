gh-flow skills

원자 스킬을 순서대로 엮는 조합(composition) 스킬들. 각 단계는 그 단계를 소유한 스킬 — gh-issue:implement, gh-pr:commit, gh-pr:create, gh-verify:review-all, gh-resolve:* — 에 그대로 위임하고, 여기서는 아무 원자도 다시 구현하지 않습니다.

이슈 #N─▶ implement─▶ commit─▶ create─▶ review-all─▶ rebase-sync
체인은 리뷰 앞에서 끝납니다 — 어느 스킬도 PR 을 스스로 머지하지 않고, 그건 사람의 판단으로 남습니다(drain --merge 만 예외이고, 그마저 gh-pr:merge-train 에 위임합니다). 체인 스킬은 첫 실패 지점에서 즉시 멈추고 재개 힌트를 담은 리포트를 냅니다 — 실패한 단계를 재시도하거나 건너뛰지 않습니다. 전제조건: 전용 worktree 의 feature 브랜치, 그리고 원자 스킬 플러그인(gh-issue · gh-pr · gh-verify · gh-resolve) 설치.

1조합 스킬

issue

/gh-flow:issue <이슈번호> [remote]

이슈 번호 1건을 원자 스킬 6개로 체인한다 — 구현, 커밋, PR, 품질 게이트, conflict · outdated rebase, 메트릭 코멘트. 구현은 direct 모드 전용이라 계획이나 brainstorming 이 필요하면 이 스킬이 아니다.

설명서 사용 예시

autopilot

/gh-flow:autopilot [spec-path] [--mode sdd|inline]

승인된 spec 하나에서 한 단계 앞부터 시작한다 — 구현 계획을 쓰고 추적 이슈를 직접 만든 뒤 구현 · PR · 리뷰 답변까지 승인 체크인 없이 진행한다. spec 작성 자체(Stage-A)는 범위 밖이고, spec 없이는 실행하지 않는다.

설명서 사용 예시

issue-relay

/gh-flow:issue-relay <이슈번호> --remote <name>

push 가 막힌 목적지 remote 에 이미 등록된 이슈에서 출발해 브랜치를 따고, 구현을 서브에이전트에 위임한 뒤 Advisor 가 diff 와 테스트를 직접 확인하고, 커밋을 relay-merge 에 넘긴다. 이슈 등록은 하지 않는다.

설명서 사용 예시

relay-merge

/gh-flow:relay-merge <PR#> | --commits <base>..<head>

먼저 버려질 ref 로 실제 push 를 프로브해서, 통하면 gh-pr:create 에 위임하고 멈춘다 — 릴레이는 폴백이지 기본이 아니다. 403 으로 차단이 확인될 때만 커밋별 패치를 gist 로 올리고 git am apply-guide 를 코멘트로 남긴다.

설명서 사용 예시

2고르는 기준 — 어디서 시작하고, 목적지가 push 를 받는가

이 스킬들은 두 축으로 갈립니다. 하나는 손에 든 것이 이슈 번호인지 spec 인지, 다른 하나는 커밋이 갈 remote 가 평범한 git push 를 받아주는지입니다.

시작점 — issue / autopilot

issue 는 이슈가 이미 있고 무엇을 만들지도 이미 적혀 있을 때다 — spec 을 지어내지 않는다. autopilot 은 spec 에서 시작해 계획과 추적 이슈를 스스로 만들며, spec 을 건너뛰는 것은 거부한다. 둘 다 리뷰 직후에 손을 뗀다.

목적지 — issue-relay / relay-merge

issue-relay 는 issue 와 같은 모양이되 마지막 칸이 PR 대신 릴레이 위임이다. relay-merge 는 그 마지막 칸 하나만 떼어낸 것이고, 프로브에서 push 가 통하면 어느 쪽도 릴레이하지 않는다.

autopilot 체인

spec─▶ writing-plans─▶ issue:create─▶ 구현─▶ pr:create─▶ simplify─▶ pr:reply

relay 체인

이슈 #N─▶ 브랜치─▶ Worker 구현─▶ Advisor 검증─▶ push 프로브─▶ patch + gist

체인 사이의 대화 텍스트가 곧 조기 종료의 원인이 되어 왔습니다 — 중간 요약 한 줄이 최종 답변처럼 읽혀 체인이 절반에서 끝나는 실패가 반복됐습니다. 그래서 --no-next-hint, Skill() 호출 사이의 텍스트 0, 그리고 하네스 Stop hook 이 세 겹으로 걸려 있고, 단계 마커와 리포트 문자열은 산문이 아니라 그 hook 과의 계약입니다.
